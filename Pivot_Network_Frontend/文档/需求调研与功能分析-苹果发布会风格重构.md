## 摘要

本次重构的实质，不是"给页面换个皮肤"，而是**把一个已经跑通但只有开发者看得懂的主链，用非专业观众也能看懂的方式重新讲一遍**。后端主链（卖家接入→验收→商品化→下单→授权→运行时会话→加密隧道→Shell/Workspace/Task）已有实现与测试；前端 6 个页面能"看起来像产品"，但数据全部来自 mock，下单、授权、会话控制都是本地状态伪造。因此发布会叙事必须建立在"真实存在的机制"上（验收、隔离、可观测），而不是建立在"真实存在的运营数据"上。

**5 条核心结论：**

1. **主链真实、前端演示级。** 后端已注册 7 组共 41 个路由（auth 4 / health 3 / files 2 / nodes 6 / capability 1 / seller onboarding 13 / trade 12），`tests/` 有 10 个测试文件；前端 `services/api` 7 个文件全部走 `useMock = true`（`src/services/api/client.ts:10`），且 `client.get/post` 的 mock 分发器 `mockData()` 直接 `return null`（`client.ts:41-43`），真实 API 从未被调用。
2. **"下单→会话"闭环已实现但是本地伪造。** `CheckoutDrawer` → `offers.createOrder()` → `sessionStore.createSession()` 全为同步本地改状态，无订单实体、无授权对象、无异步、无失败分支；`orders.ts` / `grants.ts` / `sessions.ts` / `auth.ts` 四个 domain 未被任何 view/store 引用，属"对齐了路径但没有调用"的死代码。
3. **现有 UI 资产足以支撑发布会叙事，但缺"第一屏"。** 16 个组件、9 个领域类型、3 个 Pinia store、6 个页面视图构成可复用底座；V2 外壳（设计 tokens、玻璃导航、⌘K 命令面板、滚动进度、`v-reveal` 指令）已由团队落地；**发布会 Landing 页在报告撰写期间才开始落地**——`nav.ts` 先加"首页 /"，随后 `router/index.ts` 才把 `/` 指向 `LandingView.vue` 并补 404、`scrollBehavior`、`afterEach` 标题。截至定稿，Landing 骨架、三幕组件位与路由已通，但三幕文案与双 CTA 的验收尚未完成。
4. **体验缺口集中在"决策与反馈"，而不是"页面数量"。** 0 处搜索/筛选/排序/分页/详情页；0 处 error 状态（`src/stores` 与 `services/api` 全目录无 `catch`/错误分支）；无登录鉴权、无路由守卫；404 仅 redirect 占位；价格原版只展示单价（`CheckoutDrawer.vue:34`），V2 已补预估费用；V1 样式无深色模式与 `prefers-reduced-motion`（V2 的 `base.css:972` 已补，断点改为 1120/860/640）。
5. **竞品对标显示，Pivot 的差异点不是"更便宜"，而是"个人供给 + 平台验收 + 会话隔离"三者同时成立。** Vast.ai/RunPod/Lambda 卖"小时级 GPU 现货+镜像"，AutoDL/恒源云卖"开箱即用的科研环境"，io.net/Akash 卖"聚合闲置供给+去中心化结算"，阿里云 PAI/华为云 ModelArts 卖"全托管 MLOps"。Pivot 相对它们唯一不可替代的叙事资产，是"买家拿到的是平台编排的 RuntimeSession，而不是卖家宿主机"这一隔离语义。

## 2 项目现状基线（代码级）

### 2.1 定位与主链

Pivot Network 是"个人/共享算力交易平台"：卖家把闲置 GPU 机器接入平台，平台验收后商品化成 Offer，买家下单获得 AccessGrant，再由平台编排出一个隔离的 RuntimeSession（Docker Swarm + WireGuard），买家通过本地 Buyer_Client 隧道在浏览器里使用 shell / workspace / task。核心主链是：

> **Seller → Verified Node → Offer → Order → AccessGrant → RuntimeSession → WireGuard → Shell / Workspace / Task**

一个必要的语义澄清（对答辩很重要）：买家**不是** SSH 到卖家宿主机，而是进入平台编排的运行时实例；卖家机器只是被"池化"成可调度的算力来源。这是 Pivot 与"二手 GPU 转租"最本质的区别，也是发布会第二幕应当反复强调的一句话。

### 2.2 技术栈与工程规模

**读矩阵**：Pivot 在两列上具备与头部产品同级的真实能力——**资源接入（个人供给+验收）**与**安全隔离（运行时会话）**；而在"计费、可观测、开发者体验"三列明显落后。发布会若把重心放在"我们也支持 A100 训练"这类同质化卖点，会输给云厂商；把重心放在"个人算力如何被安全地组织起来"，才是差异化。

### 3.4 六条市场结论

1. **个人供给的市场已被验证，但"验收"是分水岭。** Vast.ai 用分级验证、RunPod 用 Secure/Community 双档，都在解决"如何让人相信陌生供给"。Pivot 的后端 onboarding + capability assessment + Verified Node 恰好是同一命题，应当在发布会里被显性化，而不是藏在卖家控制台里。
2. **计费颗粒度是体验基线，不是加分项。** 头部产品普遍做到按秒/按小时、明细可查；Pivot 当前只有 `price` 与 `unit` 两个展示字段，**这是本次重构无法在纯前端补齐的硬需求（P0 可为"计费预览"，真实计费必须后端）**。
3. **"镜像/模板"决定买家决策成本。** AutoDL/恒源云靠预置镜像把"从零配环境"变成"点一下就能跑"；Pivot 已有算法工坊的雏形（3 个模板），但卡片不可点击、不能一键下单，等于没有发挥价值。
4. **SSH/Jupyter 是专业用户的"熟悉感锚点"。** 越是工程用户，越在意"我能不能像以前一样用"；Pivot 的 shell/workspace/task 三件套需要一句"你熟悉的工作方式，仍然可用"来降低心理门槛。
5. **去中心化平台的信任成本极高。** io.net/Akash 的争议说明"供给未经治理"会反噬产品；Pivot 应把"平台验收、平台编排、平台可关停"作为卖点，而不是把"去中心化"当口号。
6. **云厂商的能力面不可能正面竞争。** PAI/ModelArts 的能力清单是 Pivot 的 10 倍以上，发布会应承认边界（"我们不替代云，我们组织闲置算力"），反而更可信。

### 4.2 卖家画像与 JTBD

- **目标**：把闲置机器变成持续、可控、不打扰自己的收入。
- **痛点**：① 接入流程像"部署一套系统"，不愿投入；② 怕被陌生人跑满、怕被用来做违规内容；③ 不知道定多少钱；④ 担心平台跑路/结算不透明；⑤ 机器 Windows 环境，担心不兼容。
- **JTBD**：「当我有一台空闲 GPU 机器时，我想用最少的配置把它接入平台、设定我能接受的价格与可用时段，并且随时可以暂停或下架——这样我能在不影响自己使用的前提下拿到收益。」
- **关键场景**：首次接入 → 验收等待 → 收到第一笔调度 → 需要自用时暂停 → 查看收益与评价。
- **拒绝点（发布会必须回应）**：_"我的机器会不会被控制？"_（答：平台只调度运行时，不接管宿主机）、_"步骤会不会很复杂？"_（答：一条命令 + 平台分阶段验证）、_"钱怎么结算？"_（答：本版本为课程原型，结算流程见后续规划，不夸大）。

### 4.3 买家画像与 JTBD

| 画像 | 目标 | 痛点 | JTBD 句式 | 对界面提出的硬要求 |
| --- | --- | --- | --- | --- |
| A 科研学生 | 用最低成本把论文实验跑出来 | 环境配置耗时、预算有限、GPU 型号不懂 | 「当我要跑一个实验时，我想在 3 分钟内找到能跑且便宜的机器并进入环境，这样我不用花一天配环境。」 | 价格透明、镜像/模板、按小时、一键进入环境 |
| B 算法工程师 | 可复现、稳定地训练/推理 | 版本漂移、环境不一致、无法自动化 | 「当我要把训练跑起来时，我想要可复现的运行时和可脚本化的入口，这样团队里任何人跑出来的结果一致。」 | 固定镜像版本、SSH/API、日志可下载 |

### 4.4 运营/运维画像与 JTBD

- **目标**：让平台"看得见、控得住、说得清"。
- **痛点**：节点掉线、会话卡死、订单/授权状态不一致、缺少抓手；现有前端只有只读 mock 监控，无法排障。
- **JTBD**：「当平台出现异常时，我想在一个页面看到节点、会话、授权三者的状态与错误摘要，这样我能在用户投诉前定位问题。」

### 8.4 深色模式与对比度

**策略**：V2 明确 `color-scheme: dark`（`tokens.css:7`），即"纯黑舞台"是**唯一模式**，不做浅色适配。这符合发布会场景，但必须在文档中明示，避免被理解为"深色模式缺失"。V1 的 `prefers-color-scheme` 为 0 处，属另一套浅色视觉，重构后整体替换。

按 WCAG 2.1 相对亮度公式（`L = 0.2126R + 0.7152G + 0.0722B`，sRGB 线性化后计算）对 V2 tokens 逐一校验：

| 前景 / 背景 | 对比度 | 判定 | 使用建议 |
| --- | --- | --- | --- |
| `--text #f5f5f7` / `#000` | **19.3:1** | ✅ AAA | 正文/标题均可 |
| `--text-2 #a1a1a6` / `#000` | **9.1:1** | ✅ AAA | 次级正文 |
| `--text-3 #6e6e73` / `#000` | **4.14:1** | ⚠️ **未达 AA 正文（4.5:1）** | 仅用于 ≥18.66px 粗体或 caption；建议提亮到 `#8e8e93`（≈6.4:1） |
| `--text-4 #48484a` / `#000` | **2.30:1** | ❌ 不达 AA | 仅装饰/发丝线，不可承载文字 |
| `--blue #2997ff` / `#000` | **6.96:1** | ✅ AA | 链接、Ghost 按钮可 |
| `--blue-deep #0071e3` 上的白字 | **4.70:1** | ⚠️ 临界通过 AA | Primary 按钮文字达标但余量小，避免再叠透明层 |
| `--blue-deep #0071e3` 作为文字色 / `#000` | **4.47:1** | ⚠️ 临界未过 | 不要用 `#0071e3` 当正文链接色，用 `#2997ff` |
| `--green #30d158` / `#000` | **10.4:1** | ✅ AAA | 健康/成功态 |
| `--orange #ff9f0a` / `#000` | **10.2:1** | ✅ AAA | 警告态 |
| `--red #ff453a` / `#000` | **6.16:1** | ✅ AA | 异常态 |
| 面板上的 `--text-2`（`rgba(255,255,255,.035)` 叠黑 ≈ `#090909`） | **≈8.6:1** | ✅ AA | 面板内文仍可读 |

结论：**4 处需要在重构中明确处理**——`--text-3` 提亮或限制用途、`--text-4` 不承载文字、`#0071e3` 只做按钮底不做文字色、Primary 按钮不要叠半透明遮罩。这是本次重构最容易"看起来高级但答辩被挑刺"的地方。

### 9.3 发布页 3 幕叙事结构（供 Lead 写文案直接使用）

**建议故事线（一句话）**：**别人卖的是 GPU 的小时，Pivot 交付的是"把闲置机器变成敢买、敢用、可隔离运行的算力"的整条主链。**

| 幕 | 核心问题 | 观众心里的疑问 | 该幕要给出的答案 | 视觉与动效 | 使用的真实素材 |
| --- | --- | --- | --- | --- | --- |
| **第一幕：问题**（约占 35% 篇幅） | 闲置算力为什么卖不出去？ | "这跟我有什么关系？" | 三道墙：**接入墙**（机器没验收，平台不敢卖）、**交易墙**（没有凭证，买家不敢买）、**运行墙**（给了 IP 等于把整台机器交出去） | 纯黑底 + 大字号断言句逐条上浮；三个数字/图标依次点亮；不出现产品 UI | 后端卖家 onboarding 需 13 个端点/多阶段 probe（说明接入复杂）；`PROJECT.md` 三条稳定性边界（说明"真实跑起来有多难"） |
| **第二幕：能力**（约占 45%） | Pivot 怎么解决这三道墙？ | "你凭什么能做到？" | 主链 7 段逐段点亮：**Seller（一条命令接入）→ Verified Node（验收：Ready + 真实任务跑通）→ Offer（商品化）→ Order（下单锁定）→ AccessGrant（一次性凭证）→ RuntimeSession（隔离运行时）→ WireGuard（加密隧道）→ Shell/Workspace/Task**；三个证明：**验收、隔离、可观测** | 横向时间轴随滚动点亮（IntersectionObserver，reduced-motion 时静态显示）；每段配真实界面截图/组件示意（市场卡、会话中心、监控节点）；关键数字 count-up（如 41 个后端端点、7 段主链） | 后端 41 个路由、`types/domain.ts` 的 Offer/Session 字段、`platform.mock.ts` 的 3 条 Offer 示例（**标注"示例数据"**）、监控页 4 节点 |
| **第三幕：行动**（约占 20%） | 我现在能做什么？ | "下一步点哪？" | 双入口：**我要算力 → `/marketplace`**、**我要出租 → `/seller`**；一句话定位 + 仓库链接 + One more thing（留给 Lead 的钩子，例如"这台机器现在就在某个实验室里闲着"） | 大留白 + 1 个 Primary CTA + 1 个 Ghost CTA；页脚"演示数据"声明 | `SiteNav` CTA 逻辑、路由 |

**三幕写作约束（避免答辩翻车）：**

1. **不写排名/第一/领先**，只写机制与事实（"平台验收后才能上架"而不是"最安全的平台"）。
2. **不编运营数字**：所有出现的数字要么来自代码（41 个端点、7 段主链、10 个测试文件），要么明确标"示例数据"。
3. **第一幕不要用产品截图**，让"问题"独立成立；第二幕才出现 UI，形成"问题→解法"的因果。
4. **每幕只讲一个中心句**，其余为证据；发布会文案的密度应当是"一屏一句"。
5. **第三幕必须有且只有一个显性 Primary**，次级 CTA 用 Ghost/描边。
6. One more thing 建议用"边界/开源/下一步"收尾，避免承诺未实现功能。

**建议的屏幕节奏（Landing 7 个区块，与设计系统一致）：**

Hero（定位 + 双 CTA）→ 技术带走马灯（Docker Swarm · WireGuard · FastAPI · PostgreSQL · Vue3 · Vite）→ 第一幕三痛点 → 第二幕主链时间轴 → 六个模块 2×3（总览/市场/算法/监控/卖家/会话）→ 安全边界（隔离语义）→ 第三幕 CTA + One more thing。

## 10 结论与后续建议

1. **本次重构的本质是"叙事重构 + 外壳重构"，不是"功能重构"。** 真正能撑起发布会的内容已经存在：后端 7 组 41 路由与 10 个测试、端到端主链、验收/隔离语义、6 页可演示界面、V2 设计系统与外壳骨架。需要补的是"第一屏（Landing）"与"选择/反馈"这一层，而不是再造一个产品。
2. **最大的风险不是做不出来，而是"说过头"。** 前端数据全部来自 mock，下单/会话为本地状态；一旦发布页把示例数据当运营成绩讲，答辩会被直接质疑。把"演示数据"声明、真实机制数字（41 端点/7 段主链/10 测试）和诚实边界（不替代云厂商、结算为规划能力）讲清楚，反而更有说服力。
3. **差异化叙事只有一句话值得反复说**：买家拿到的是平台编排的隔离运行时，而不是卖家宿主机；卖家的机器要经过平台验收才能上架。这是竞品矩阵里 Pivot 唯一同时具备、且大厂与去中心化平台都不完全具备的组合。
